### Draft: "Your MCP server is stateless. That's why the agent is flailing."

- **Misconception hook:** tool builders ask "is my API well-designed?" —
  clean REST, good docs, idempotency. You can pass that whole checklist and
  still have built a bad tool, because the checklist is for human callers.
- **Question up front:** what does a tool have to know that a human user
  would never need it to?
- **A-plot:** statefulness unpacked into concrete properties — know the
  session; reveal capabilities progressively instead of dumping forty tools;
  make invalid orderings impossible rather than documented; let the agent pin
  its focus; assume the agent's memory of you gets compacted away mid-task.
  Then the provocation: after all this, a plain CLI often beats an MCP
  server, because bash is the interface models already know.
- **B-plot:** one war story per property — the cursor-tracking fix for lazy
  offset use (the founding anecdote); the polling shell tool paying per
  glance where a human waits for free; 256 file descriptors; side-chat
  latency; the embedding-API outage that argues for boring dependencies.
- **Close:** flip the question — not "would a developer like this API" but
  "would it survive a caller with amnesia and a token meter."
